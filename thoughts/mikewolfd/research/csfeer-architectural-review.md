# CSFeer Architectural Review

**Date:** 2026-02-17
**Reviewer perspective:** Solutions architect, first encounter with codebase
**Scope:** Point-in-time snapshot of a proof of concept. This documents the current architecture, not a target state. See `research/analysis/` for exploration of future directions.

## What Is This Thing?

CSFeer is a **government form management system** built by Focus Consulting for ACF (Administration for Children and Families). It handles tribal CSBG (Community Services Block Grant) reporting forms - multi-page, multi-step wizards with conditional logic, calculated fields, audit trails, and PDF export.

Production auth goes through **login.gov**. It deploys on **AWS EKS** with Aurora PostgreSQL. The UI follows **USWDS** (U.S. Web Design System) requirements.

It's a Django 6 app. Server-rendered. Not an SPA.
(`uv.lock` resolves Django to 6.0; `csfeer/settings.py` still has a stale "Generated by Django 5.2.7" header comment.)

## The Layers, Honestly Assessed

### 1. Django Project Structure

**Apps:** `core`, `users`, `form_manager`, `django_cotton_uswds`

The structure is clean. `core` provides a `BaseModel` (UUID PK + timestamps). `users` has a custom email-based user model (`CoreUser` with `CoreUserManager` in `users/managers.py` for email-based creation) with OIDC profile. `form_manager` is where the domain lives. `django_cotton_uswds` wraps USWDS markup into reusable template components.

**Additional installed third-party apps:**
- `crispy_forms` with a custom USWDS template pack (`CRISPY_TEMPLATE_PACK = "uswds"`) - suggests a dual form rendering strategy alongside cotton components
- `django_extensions` - provides shell_plus, graph_models, and management commands
- `django_json_widget` - provides a JSON editor widget used in Django admin (configured on `FormEntryAdmin` for editing `FormEntry.data` via `formfield_overrides` on all JSONFields)
- `django.forms` is explicitly listed in INSTALLED_APPS to override the default form template location

**Settings** use Pydantic for type-safe config. Environment variables with nested delimiter support (`DB_CONFIG__PGHOST`).

The database config is more deliberate than the usual Django default:
- Custom backend `csfeer.postgresql` generates an RDS IAM auth token via `boto3` when `DB_CONFIG__USE_IAM_AUTH=True`.
- `CONN_MAX_AGE` is set to 14 minutes to align with the ~15 minute IAM token lifetime.
- `statement_timeout` is set at the connection level (default `3600000` ms, 1 hour).
- `POOL=True` and `CONN_HEALTH_CHECKS=True` are enabled (good intent, but verify the Django/psycopg driver combination supports the pooling mode you expect).

**Management commands** (`form_manager/management/commands/`):

| Command | Purpose | Notes |
| --- | --- | --- |
| `load_initial_forms` | Sync Python form schemas into FormDefinition DB records | **Critical for deployment** - bootstraps form definitions; `--force` to overwrite existing |
| `dump_schema` | Export form schemas as JSON Schema | Lists or dumps Pydantic form schemas; supports `--name` and `--list` flags |
| `generate_er_diagram` | Create ER diagrams via django-extensions `graph_models` | Outputs to `docs/app/erds/`; also wired as a pre-commit hook on `models.py` changes |
| `nuke_forms` | Delete all form data (FormEntry, FormDefinition, audit records) | **Destructive** - requires `yes` confirmation |
| `seed_demo_org` | Create a "Demo Organization" and assign users as editors | `--email` for one user, `--all` for everyone |

Static delivery is duplicated:
- `whitenoise.middleware.WhiteNoiseMiddleware` is enabled in `csfeer/settings.py`.
- The container/K8s design also includes an nginx static server container (see below).

**Verdict:** Sensible app boundaries. No bloat. The Pydantic settings pattern is a good choice.

### 2. The Form Engine (Core Domain)

This is the heart of the system and it's **genuinely well-designed**.

The architecture fuses **Pydantic models** (form definitions, validation rules, UI layout) with **Django forms** (field rendering, widget system, server-side validation). A metaclass (`ACFFieldsMeta`) dynamically generates ACF-prefixed versions of all standard Django field types, adding metadata like `title`, `review_title`, `description`, and `default_if_excluded`.

**Form lifecycle (model statuses):**
```
Draft (multi-page edit) → Submitted → [Amended] → [Archived]
                                ↕
                           Lock/Unlock
```
Note: "Review" is a UI step (a read-only summary page before submission), not a model status. The actual `FormEntry.status` choices are: `draft`, `submitted`, `amended`, `archived`.

**Key domain concepts:**

| Concept             | What It Does                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `FormDefinition`    | Template for a form type. Has a `schema_class` string pointing to a Python class and a `schema` JSONField. Versioned with SemVer. |
| `FormEntry`         | An instance of a form being filled out. Stores data as JSON. Scoped to an organization.                                           |
| `FieldFilterField`  | A checkbox field that controls which other fields are visible. Drives conditional page/section exclusion.                         |
| `CalculatedField`   | Auto-computes values from other fields (sums). Disabled, non-editable.                                                            |
| `CurrencyField`     | Decimal field with Alpine.js masking for display formatting.                                                                      |
| `YesNoDisplayField` | MultiValueField: radio (yes/no) + conditional sub-field.                                                                          |
| Layout tree         | 8 block types inheriting from `RenderableBaseModel` (see below). Recursive, renderable, prunable.                                  |

**Layout block types** (`form_manager/schema/layout.py`):

| Block | Purpose |
| --- | --- |
| `RenderableBaseModel` | Generic base - fuses Django's `RenderableMixin` with Pydantic `BaseModel`. Provides `get_context()`, `as_review_block()`, recursive `has_field_blocks()`. |
| `StepBlock` | Top-level wizard step. Children: PageBlock, PermanentPageBlock, SectionBlock. |
| `AbstractPageBlock` | ABC base for page variants. |
| `PageBlock` | A page within a step. Can be excluded via FieldFilterField. Children: FieldBlock, SectionBlock, FieldGroupBlock. |
| `PermanentPageBlock` | Like PageBlock but never excluded by filter fields. |
| `SectionBlock` | Groups fields under a heading. Children: FieldBlock, FieldGroupBlock, ReviewSubheadingBlock. |
| `FieldGroupBlock` | Border-wrapped field group with explanation text (`form_manager/field_group.html`). |
| `FieldBlock` | Leaf node binding a form field to the layout. `as_review_block()` auto-discovers field-type-specific review templates (e.g., `currency_review.html`). |
| `ReviewSubheadingBlock` | Review-only subheading. Only renders on the review page. |

**Widget classes** (`form_manager/schema/widgets.py`):

| Widget | Base | Template |
| --- | --- | --- |
| `CurrencyInput` | `forms.NumberInput` | `form_manager/widgets/currency.html` |
| `CheckboxSelectMultiple` | `forms.CheckboxSelectMultiple` | `form_manager/widgets/checkbox_select_multiple.html` |
| `YesNoDisplayWidget` | `forms.MultiWidget` | `form_manager/widgets/yes_no_display.html` - `decompress()` splits dash-delimited values |

**Template tags** (`form_manager/templatetags/form_manager_tags.py`):
- `flatten_for_review` filter - recursively transforms the nested layout tree into a flat list of steps, each containing only `FieldBlock` and `ReviewSubheadingBlock` instances with `title`, `edit_url`, and `blocks` keys. This is the bridge between the schema layer and the review page UI.

**Custom model field:** `SemVerField` (`form_manager/models/fields.py`) - Django model field for semantic versioning validation, used on `FormDefinition`.

**The schema/model split is clear:** Schema layer defines structure and behavior (stateless). Model layer persists instances and tracks changes (stateful). The Pydantic+Django form bridge is expert-level work.

**Views** (`form_manager/views/`):

Base classes in `form_manager/views/base.py`:
- `BaseFormUpdateView` - Modified `UpdateView` compatible with basic Django forms instead of ModelForms
- `BaseSingleFormView` - Provides common form logic: schema import, form class generation, initial data from `FormEntry`
- `BaseFormPermissionMixin` / `FormPermissionMixin` - Permission checks (`can_edit`, `can_submit`, `can_view`) and locked-state logic

| View | Type | Purpose |
| --- | --- | --- |
| `form_list` | FBV | Lists non-archived form entries for user's org + active form definitions |
| `form_start` | FBV | Creates new `FormEntry` with incremented version number, creates audit trail |
| `form_edit` | CBV | Multi-page form editing with per-step validation |
| `form_review` | CBV | Read-only summary page before submission; sets `show_errors` session flag |
| `form_finalize` | CBV | Transitions entry to `submitted` status (validation currently commented out) |
| `FormDownloadView` | CBV | Synchronous PDF generation via weasyprint |
| `FormPreviewView` | CBV | Read-only preview (requires view permission) |
| `form_history` | FBV | Shows submission events (submit/amend) and all audit trail entries |
| `FormSnapshotView` | CBV | Displays form state at a specific audit trail timestamp via `reconstruct_state()` |
| `lock_form` / `unlock_form` / `archive_form` | FBVs | State transitions on form entries |

**Audit system:** Two-tier - `FormAuditTrail` for actions (create, save, submit), `FormAuditDetail` for field-level diffs. Supports state reconstruction at any point in time. The `form_history` and `FormSnapshotView` views expose this as a time-travel UI.

**Verdict:** This is the strongest part of the codebase. The conditional field logic, calculated fields, and recursive layout tree are complex but well-isolated. Someone who understands government forms built this.

### 3. Frontend

**Architecture:** Server-rendered Django templates + Alpine.js sprinkles. No SPA.

- **django-cotton** provides 93 USWDS components (`<c-alert>`, `<c-button>`, `<c-card>`, etc.)
- **Alpine.js** + **@alpinejs/mask** handles: calculated field updates, yes/no conditional display, download confirmation modals, currency input masking (`$money($input, '.', ',')`)
- **USWDS JavaScript** (`@uswds/uswds`) is imported in `global.js` for interactive components (accordions, date pickers, modals, etc.) - not just SCSS
- **Webpack** bundles USWDS SCSS/JS + Alpine.js + mask plugin into three outputs: `global.bundle.js`, `styles.bundle.js` (empty artifact from CSS entry point), and `styles.css`
- **HTMX** is installed but **completely unused** - dead dependency

**Frontend JS beyond Alpine sprinkles** (`frontend/src/js/`):
- `global.js` - Entry point. Imports USWDS JS, Alpine.js + mask plugin, and exposes `updateCalculatedFields` globally.
- `utils/forms.js` - `updateCalculatedFields()` function (lines 12-28). Sums values from `data-source-fields` attributes on `.calculated-field` and `.calculated-currency-field` elements, formats output via `Intl.NumberFormat` with 2 decimal places. This is the glue between Alpine.js change events in templates and the calculated field DOM updates.

**Custom SCSS** (`frontend/src/scss/`):
- `_uswds-theme.scss` - USWDS theme configuration: custom color tokens (accordions, cards, tables, summary boxes), font weights, image/font paths.
- `_uswds-theme-custom-styles.scss` - 183 lines of custom styling: flexbox layout system, form field/label/error customization, button styling, switch/toggle components, form validation states, responsive overrides, and user navigation header.

The component library has a pattern library (django-pattern-library) with YAML configs and markdown docs. Progressive enhancement works correctly - forms submit without JS.

**Note on asset layout:** `csfeer/static/frontend` is a local-only symlink to `frontend/built/` (the compiled Webpack output), gitignored for development convenience. Both `frontend/built` and the symlink are excluded from version control via `.gitignore`.

**Verdict:** Appropriate technology choices for a government form app. The cotton component library is well-organized. Remove HTMX.

### 4. Authentication & Authorization

**Auth flow:** OIDC via `django-oauth2-authcodeflow`. Keycloak for dev, login.gov for production.

Custom `EmailOIDCAuthenticationBackend` provisions users on first login. Role sync happens every login via `extend_user_with_roles` hook (`OIDC_EXTEND_USER` setting): Keycloak `realm_access.roles` are mapped to Django groups, and `is_staff`/`is_superuser` flags are set accordingly. A personal organization is auto-created for new users.

**OIDC middleware stack** (three middleware components, not just login enforcement):
- `LoginRequiredMiddleware` - Redirects unauthenticated users to OIDC login (skips `api/` and `logged-out` paths)
- `RefreshAccessTokenMiddleware` - Auto-refreshes OIDC access tokens before expiration
- `RefreshSessionMiddleware` - Auto-refreshes Django sessions to prevent logout during active use

**Roles:**
- `csfeer_admin` → staff + superuser
- `csfeer_staff` → staff
- `csfeer_user` → standard user
- Organization-level: admin, editor, viewer (via `UserOrganizationMembership`)

**Note:** `user.groups.clear()` runs on every login. Manually assigned Django groups get wiped. This is by design (OIDC as source of truth) but worth knowing.

**Verdict:** Solid. No passwords in the database. IAM tokens for DB access in production. The dual-level permission model (system roles + org roles) is appropriate for the domain.

**API surface (what's actually implemented):**

Django Ninja API mounted at `/api/v1/` (`csfeer/urls.py`). Auth is `django_auth` (session auth). OIDC middleware skips `api/` paths so unauthenticated calls get 401/403 instead of redirect loops. CSRF is auto-exempted by Django Ninja internally. No CORS configuration exists anywhere in the project.

**All 7 endpoints (read-only GETs, all tagged "Forms"):**

| Endpoint | Purpose | Scoping |
| --- | --- | --- |
| `GET /forms/definitions` | List active form definitions | **No org scoping** - all authenticated users see all definitions |
| `GET /forms/definitions/{id}` | Get specific definition (includes full JSON schema + Python class path) | None |
| `GET /forms/definitions/{id}/entries` | List entries for a definition | Filtered by user's org; optional `status` and `include_archived` filters |
| `GET /forms/entries/{id}` | Get entry with **full `data` JSON** | Org permission check via `user_can_view()` |
| `GET /forms/entries/{id}/audit-trail` | Audit trail actions | Org permission check |
| `GET /forms/entries/{id}/audit-details` | Field-level audit changes (exposes `old_value`/`new_value`) | Org permission check |
| `GET /forms/organizations/me` | Current user's org (name, address, contact email, phone) | Own org only |

**API schemas** (`form_manager/api/schemas.py`) - data exposure concerns:
- `FormEntrySchema` exposes the entire `data` JSON field - this contains all user-submitted form values, potentially including PII
- `AuditDetailSchema` exposes `old_value`/`new_value` pairs - field-level PII in change history
- `FormDefinitionSchema` exposes `schema_class` (internal Python import path) and full `schema` JSON
- `OrganizationSchema` exposes full contact details (address, email, phone)

**What the API lacks:**
- **No pagination** - all list endpoints return unbounded result sets
- **No rate limiting** - zero throttling on any endpoint
- **No CORS headers** - not configured anywhere
- **No API-specific tests** - zero test coverage for any of the 7 endpoints
- **N+1 query risk** - audit trail/detail endpoints lack `select_related()` on user FK
- OpenAPI docs are auto-generated by Django Ninja at `/api/v1/docs` and `/api/v1/openapi.json`

**Django admin** is enabled at `/admin/` and fully configured:
- `FormEntryAdmin` - displays status/locked flags, provides PDF download links, uses `JSONEditorWidget` for the data field
- `FormDefinitionAdmin` - list display with family/name/variant/active, filters and search
- `FormAuditTrailAdmin` / `FormAuditDetailAdmin` - list display with filters by action/field name
- `CoreUserAdmin` - custom UserAdmin with email-based ordering, inline `UserProfile` editing
- `OrganizationProfileAdmin` / `UserOrganizationMembershipAdmin` - contact info display, role filtering

This is an operational interface for managing FormDefinitions and inspecting form data, not just Django boilerplate.

### 5. Infrastructure & Deployment

**Local dev:** Docker Compose with PostgreSQL 16, Keycloak, Django dev server. Makefile with 19 targets including `test-unit`, `test-e2e`, `test-e2e-webkit`, `test-e2e-debug`, `test-e2e-auth`, `reset-all`, `reset-db`, `migrate`, `load-form`, `nuke-forms`, `oauth-setup`, `build`, `start`, `start-local`, `stop`, `restart`.

**Docker Compose security hardening** (often overlooked):
- Application and infrastructure services (`mock-oauth`, `db`, `app`) run with `cap_drop: all` and `security_opt: no-new-privileges:true`
- PostgreSQL gets specific `cap_add` for required capabilities only (DAC_OVERRIDE, FOWNER, SYS_CHROOT, SETGID, SETFCAP, SETPCAP, SETUID)
- Network aliases for service discovery: `oauth.csfeer`, `db.csfeer`; app uses `hostname: ui.csfeer`
- App service runs migrations automatically via `post_start` command

**Additional Compose services:**
- `oauth-setup` - One-time init container that seeds Keycloak users from `devops/mocks/keycloak/users.csv` (username=password in dev), configures OIDC client secrets, and assigns realm roles via `kcadm.sh` CLI
- PostgreSQL init script (`devops/postgresql/initdb.d/init-db.sh`) creates a `csfeerauth` database alongside the main database for Keycloak storage

**Container runtime (what’s in the repo):**
- Prod app container runs `gunicorn --bind 0.0.0.0:8000 csfeer.wsgi:application` with no explicit worker/thread/timeout tuning (`Dockerfile`).
- Static container is `nginxinc/nginx-unprivileged` listening on `8080`, serving `/static/` and proxying `/` to the app on `8000` (`nginx.conf`).

**Kubernetes target (Helm chart intent):**
- Single Deployment with two containers (nginx static + Django app), both non-root, read-only root filesystems, with `/tmp` as an in-memory `emptyDir` (`devops/iac/kubernetes/csfeer-helm/templates/app/deployment.yaml`).
- ALB Ingress with access/connection logs to S3 and deletion protection enabled by annotation (`devops/iac/kubernetes/csfeer-helm/templates/app/ingress.yaml`).
- External Secrets Operator integration (`devops/iac/kubernetes/csfeer-helm/templates/shared/external-secret-app.yaml`).
- HPA enabled (min 2 / max 10) (`devops/iac/kubernetes/csfeer-helm/values.yaml`), but the HPA template appears miswired (see concerns below).

**Additional Helm templates** (beyond the app deployment):
- **Shared infra:** ClusterSecretStore, ConfigMap, Role, RoleBinding, ServiceAccount (`templates/shared/`)
- **Mock services:** Mock API deployment + RBAC + Service, Python shell deployment + RBAC (`templates/mock/`) - for development/testing in-cluster
- **ArgoCD:** `csfeer-argo-app.yaml` Application manifest; separate `keycloak-helm/` chart directory with Bitnami Keycloak, External Secrets, and namespace config

**Terraform (what's actually present - 3 components):**

`csfeer-rds`:
- Aurora PostgreSQL cluster (`aurora-postgresql` engine, engine_version `16.6`), storage encryption, deletion protection, IAM DB auth enabled (`devops/iac/terraform/components/csfeer-rds/csfeer-rds-aurora.tf`, `devops/iac/terraform/modules/rds-aurora/terraform/main.tf`).
- Backup retention is a variable: dev tfvars sets `7`; component default is `30`; the `csfeer-rds` README claims `14` (docs and config disagree).
- CloudWatch alarms exist for DB connections, CPU utilization, and replica lag via an SNS topic (`devops/iac/terraform/modules/rds-aurora/terraform/cloudwatch.tf`).

`csfeer`:
- KMS keys with rotation are defined for encrypting Secrets Manager secrets (`kms.tf`), and Secrets Manager secrets are declared for the app secret key + OIDC client secret + future API keys (`secrets.tf`).
- SES send-email IAM policy exists (`iam.tf`), but there's no application code in this repo using SES yet.
- S3 bucket for ALB access logging (`s3.tf`) with versioning, 90-day lifecycle policy, object lock, and SSL-only bucket policy.

`csfeer-argo`:
- ArgoCD Application manifests for the main csfeer app (`occam-manifest.tf`) and Keycloak (`keycloak-manifest.tf`) with Helm parameters
- ECR authentication: creates Kubernetes secrets for OCI registry access and authorization tokens

**DevOps utilities** (`devops/iac/utilities/`):
- `terraform_wrapper.sh` - Standardized Terraform operations across environments. Auto-selects AWS profile (`acf-csfeer`), handles backend config from tfvars, defaults to `us-east-1`, auto-cleans `.terraform/` between runs.
- `aws_state_storage_setup.sh` - Creates S3 state buckets with encryption, versioning, and public access blocking (`csfeer-{env}-tf-state-{region}`).

**Database users follow least privilege:**
| User                    | Access                |
| ----------------------- | --------------------- |
| `csfeer_app_user`       | Read/write            |
| `csfeer_migration_user` | DDL (migrations only) |
| `csfeer_admin_user`     | Admin operations      |
| `csfeer_reader_user`    | Read-only             |

**Verdict:** The intent is production-grade (IAM DB auth, encryption, ALB logging, External Secrets, non-root/read-only containers). But the deploy artifacts in this repo (Dockerfile + Helm chart) have multiple mismatches that likely prevent a successful deployment without fixes.

### 6. Testing

**Unit tests:** ~51 tests covering form validation, calculated fields, filter fields, layout blocks, views, management commands.

**E2E tests:** ~21 Playwright tests covering auth flows, role-based access, full form workflows (tribal short + long forms), calculated field reactivity, error states.

**Playwright config:** Video recording, trace capture with screenshots and snapshots. Uses Playwright's default browser (Chromium) without explicit headless configuration. Page Object Model pattern is present but minimal (only `BasePage` and `LoginPage` - 2 page objects for 21 tests).

**Test infrastructure:**
- **Faker integration** for generating test data (`tests/conftest.py:18`) - user factories with random names/emails/passwords
- **Fixture hierarchy:** `tests/conftest.py` (Playwright browser/context/page, auth fixtures), `tests/unit/form_manager/conftest.py` (seed data via management commands, form entry factory), `tests/fixtures/users.py` (test user credentials from Keycloak CSV, `admin_page`/`demo_page` fixtures, `login_as()` helper)
- **Test schema mocking** (`tests/unit/form_manager/fixtures/use_test_schema.py`) - complete `TestSchema` + `TestSchemaForm` with UI layout blocks, patched via `unittest.mock.patch` to avoid dependency on specific form definitions
- **Pytest optimizations** in `pyproject.toml`: `--reuse-db` (reuses test database between runs), `--nomigrations` (skips migration execution), `--strict-markers`
- **Custom markers:** `@pytest.mark.slow`, `@pytest.mark.integration`, `@pytest.mark.unit`, `@pytest.mark.e2e`, `@pytest.mark.auth`
- **Browser config:** 1920x1600 viewport, en-US locale, America/New_York timezone, `ignore_https_errors: True`, 30-second default timeouts
- **Test documentation:** `tests/QUICK_START.md`, `tests/README.md`, `docs/E2E_TESTING.md`

**What's missing:**
- **API endpoint tests** - zero coverage for all 7 Django Ninja endpoints (auth, authorization, response schemas, error cases)
- Integration tests (Django views without Playwright)
- Frontend JS tests
- Coverage reporting (tool installed, not configured)
- Visual regression testing

**CI/CD:** GitHub Actions workflows exist for E2E tests and pre-commit checks, but **both are set to manual trigger only** (push/PR triggers are commented out). There are no automated quality gates on PRs.

**Pre-commit hooks** (`.pre-commit-config.yaml`):
- Black formatter (v25.1.0, Python 3.12 target)
- Ruff linter with auto-fix (v0.9.4)
- Pyright type checker (v1.1.408)
- Custom local hook: `generate-er-diagrams` - runs `make create-erds` on any `models.py` change

**Makefile test targets** (6 variations):
- `test-unit` / `test-unit-with-docker` - unit tests locally or in container
- `test-e2e` / `test-e2e-headed` - headless or visible browser
- `test-e2e-debug` - slow motion (1000ms) for debugging
- `test-e2e-webkit` - WebKit browser (macOS Sequoia compatibility)
- `test-e2e-auth` - filtered to `@pytest.mark.auth` tests only

**Flaky test risk:** Heavy use of `page.wait_for_timeout()` (hardcoded waits) instead of deterministic assertions. 94 instances across all E2E tests (41 in the two tribal form test files alone).

**Verdict:** Good test foundation. The E2E coverage for core form workflows is solid. But CI/CD being disabled means none of this runs automatically, the entire API layer is untested, and the hardcoded waits are a significant flake risk. These need to change before production.

## What's Actually Good

I came in skeptical. Here's what I found:

1. **The form engine is genuinely well-architected.** The Pydantic+Django form fusion, the metaclass for field generation, the recursive layout tree, the conditional field exclusion - this handles real government form complexity without becoming a mess.

2. **Infra-level security posture is strong.** Non-root containers, IAM DB auth, OIDC everywhere, no passwords stored, capability dropping, read-only filesystems, separate migration IAM roles. Application-level hardening and privacy/logging still need attention.

3. **The audit trail is production-grade.** Action-level + field-level tracking with time-travel reconstruction. That's what government compliance requires.

4. **Infrastructure design intent is mature.** Aurora + CloudWatch alarms, HPA, External Secrets Operator, ArgoCD GitOps, least-privilege DB users. But the Helm chart and infra READMEs drift from the checked-in configuration and need cleanup to be deployable.

5. **Technology choices are appropriate.** Django for a government form app is exactly right. Alpine.js for sprinkles instead of React is the correct call. USWDS compliance via Cotton components is clean. No over-engineering.

6. **The component library is real.** 93 USWDS components with a pattern library. That's reusable infrastructure, not throwaway work.

---

## Summary Assessment

**Overall:** The form engine is the crown jewel - sophisticated but well-isolated. The repo also shows strong infra/security *intent* (IAM DB auth, encryption, non-root containers). However, there are several **production-readiness blockers visible directly in the code/config**: synchronous PDF generation, PII logged at INFO, and deploy artifacts (Dockerfile + Helm chart) that appear internally inconsistent and likely non-functional without fixes.

**What I'd prioritize:**
1. Fix the commented-out validation in `form_finalize.py` (data quality risk)
2. Remove/sanitize INFO logs that include form data (`form_manager/utils.py`) and align logging with container reality (stdout or writable volume)
3. **Harden the API layer** - add pagination to list endpoints, add rate limiting, evaluate what PII the schemas expose (`FormEntrySchema.data`, audit `old_value`/`new_value`, org contact details), configure CORS, add API tests
4. Fix prod Docker build to include all Django apps (or install the project into the venv) and verify the image boots
5. Fix Helm chart mismatches (values schema, SECRET_KEY env var, ingress healthcheck path, HPA target)
6. Enable CI/CD triggers on PRs (the workflows exist, just uncomment them)
7. Replace hardcoded Playwright waits with deterministic assertions

**What I would NOT do:**
- Rewrite the form engine (it's good)
- Add a frontend framework (Alpine.js is sufficient)
- Over-abstract the view layer (FBVs are fine for this domain)
- Add middleware or signals for things that don't need them yet
